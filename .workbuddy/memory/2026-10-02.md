## Alien Shooter v1.22DIC 中文字形渲染失败 — 逆向根因定位（★★★）

目标游戏：`I:\LocalGames\AlienShooter v1.22DIC\AlienShooter.exe`
（MD5 `641f33c3207d37a838d4f7f8f9c40e26`，32 位，MSVC，D3D9 + d3dx9_43）

### 结论
中文无法渲染是**两个硬性设计限制叠加**，不是编码/缺文件问题：
1. 引擎**逐字节**处理文本，无任何 UTF-8/GBK 双字节解码
2. `Font\001font.tga` 位图图集**只有 152 个字形，无任何 CJK**

### 渲染链路（已逐函数确认）
- `sub_426680` @ `0x426680` — 文本绘制主循环。`v20 = *(_BYTE *)(*v14 + v10)` 逐字节取码；
  仅支持 `\n` `\r` `\t` `\x1B+char`（颜色）四种转义
- `sub_417F80` @ `0x417F80` — 字形查找，`a2` 为单字节索引，上界 `this[174]`
- `PICTURE_FONT::vtbl[3] = 0x44A6A0` — 字体加载，**`*(this+2)+4 = 256` 容量写死**（`0x44A816`）
- vtable `0x4DA5D8`（`PICTURE_FONT`）/ `0x4DA6B8`（`VID_FONT`）
- `sub_44C120` @ `0x44C120` — 16 列网格切图集
- `sub_44C520` @ `0x44C520` — 图集缓冲分配
- `sub_448E20` / `sub_44BE60` — 像素读写（支持 8/16/24/32 bpp）
- `sub_44BA60` @ `0x44BA60` — 网格坐标计算（`v2[2] % 16`、`v2[2] / 16`）
- `"<Font="` @ `0x4D99CC` — 运行时切字体标签

### 001font.tga 图集规格（实测）
- 208×288，24bpp 直存 RGB
- 格宽 = 208/16 = **13px**，格高 = **18px**（墨迹占 y=0..12，13..17 恒空）
- 16 列 × 16 行 = 256 格
- **映射公式 `code = cell_index + 0x21`**（cell 0x00=`!`，0x20=`A`，0x2F=`P`）
- 覆盖：0x21-0x60 ASCII 标点/数字/大写（64）；**0x61-0xA0 全空白**；
  0xA1-0xFF 俄文 CP1251（88）。共 152 字形
- 顺带发现：**小写英文字母也显示不出来** —— 该图集自身缺陷，
  所以 `strings.ini` 全大写是为绕过此问题

### 失效机理
UTF-8「你」= `E4 BD A0` → 三字节各自查俄文表 → 0xE4 画出错的俄文字母、
0xBD 画错的俄文字母、0xA0 空白。且每字节按字宽推进 X，中文占 3 倍宽度，排版崩坏。

### 文本资源现状
`Text\*.txt` 71 个：68 纯 ASCII + 3 CP1251（俄文原版遗留）。**目前无中文语料**。

### 修复方向评估
- **方向 A（推荐）**：DLL Hook 整体替换 `sub_426680`，实现 UTF-8→字形索引转换 +
  自建 CJK 字形图集。风险点：需复刻 `Block` 结构体偏移语义
  （+12=X, +13=Y, +31=长度, +32=对齐, +34=行数, +116=文本指针, +37=字体对象）
- **方向 B**：自定义单字节编码（需配合 A 的表扩容，256 容量是硬限制）
- **方向 C**：GDI 渲染（exe 已导入 CreateFontA/ExtTextOutA，但仅覆盖部分菜单 UI，
  无法覆盖 D3D9 游戏内文字）
- **不推荐**：直接改 001font.tga 塞汉字（256 槽硬限制，改图集不解决编码识别）

### PE 安全特性（决定 hook 策略）
```
DllCharacteristics 0x8140
  DYNAMIC_BASE (ASLR) : True   ← 地址不固定，必须运行时算基址
  NX_COMPAT           : True
  NO_SEH              : False  ← 走 SEH
  GUARD_CF            : False  ← 无 Control Flow Guard
DataDirectory[10] LoadConfig RVA = 0  ← 无 SafeSEH 表、无 SEH handler 白名单
```
→ **无 SafeSEH 约束、无 CFG**，hook 方案自由度大；但 **ASLR 开启，所有地址必须
  `GetModuleHandle(NULL) + RVA` 运行时计算，不能硬编码 0x426680。**

### 两个目标函数的形态差异（关键）
- `sub_426680` @ `0x426680`（绘制循环，整体替换目标）
  入口：`push ebp / mov ebp,esp / push -1 / push SEH_426680 / mov eax,fs:[0] /
  push eax / sub esp,20h / ... / mov eax,___security_cookie / xor eax,ebp`
  → 带 **SEH frame + /GS stack cookie**，MSVC `/GS` + `/EHa`。不可裸 trampoline。
  → 引用来源：`.data` BSS 区 `0x4DA7D0`（磁盘全 0，**运行时填充的回调表**），
    说明它是被注册为对象方法/回调槽调用，不是直接 `call`。
- `sub_417F80` @ `0x417F80`（字形查找，仅观测用）
  入口：`push ebp / mov eax,[ebp+8] / test eax,eax / js / cmp eax,[ecx+2B8h] /
  jge / mov eax,[ecx+eax*4+2BCh] / test / jnz / mov eax,dword_64C4F0 / pop ebp / retn 4`
  → **11 字节 stdcall 叶子函数**，上界字段在 `this+0x2B8`，字形数组在 `this+0x2BC`。
  → 极小，inline hook / trampoline 都轻松。

### 运行时依赖
- 静态导入：`WINMM / d3d9 / d3dx9_43 / DSOUND / KERNEL32 / USER32 / GDI32 /
  COMDLG32 / ADVAPI32 / SHELL32 / ole32 / steam_api.dll`
- **`steam_api.dll` 是静态导入**（非 delay-load）→ DLL 注入必须晚于 steam_api 初始化，
  否则 `DllMain` 里调用 D3D/steam 接口会失败。建议 `DLL_PROCESS_ATTACH` 里只做最小注册，
  真正初始化放到首次调用 hook 函数时（懒初始化）。
- 注册表路径 `HKCU\SOFTWARE\SigmaTeam\AlienRus`，存档在 `saves/`。

### AlienShooter.cfg 的 GDI 字体配置（对方案 D 有用）
```ini

Font=Courier New      ; 备选 MS Sans Serif
FontSizeX=7

```
→ 说明存在 GDI 文本路径，但尺寸写死 7x8，且 D3D9 主画面不走它。

### minhook 结论
**主 hook（替换 sub_426680）不需要 minhook**：因为是「整函数替换」而非「改函数中段」，
入口 `mov eax, imm32` 或 `jmp rel32` 即可，无需 trampoline 转发回原函数。
手写 5 字节 `E9` + 存原函数指针即可，比引入 minhook 更轻。

**但仍建议集成 minhook**，理由：
1. 后续若要 hook 别的函数（如 `sub_417F80` 观测码位分布、`sub_4306A0`），
   多点 hook 用 minhook 省事且不易出错
2. minhook 自带 `MH_Initialize` / `MH_CreateHook` / 指令边界自动处理，
   对 `sub_417F80` 这种小函数比自己算指令长度稳
3. 后续若改走「hook 函数中段 + 回跳原逻辑」路线，minhook 的 trampoline 是必需的
→ 建议**集成但不依赖**：核心替换自己写 E9 跳板，其余观察点用 minhook。

### 关键格式发现
- 源文本是**硬换行定宽**（英文按 ~28 半角字符折行），**引擎不做自动换行**
  → 译文必须沿用同样折行策略，否则撑破 UI 文本框
- 分区标记：`MISSION NN / DESCRIPTION / TIPS / OBJECTIVE / PARAMETERS`
  → 译为 `任务 NN / 任务简报（关卡）或描述（道具武器）/ 提示 / 目标 / 参数`
  → 校验器强制「分区数与英文基线一一对齐」，丢一个标记就少一块 UI
- 全部 CRLF；结尾有无换行逐文件与原文一致（END_NL 集合）
- 4 文件原文即为空（`addon2end_01/02`、`addon_end_01~04`），保持 0 字节

### 踩过的坑
1. **构建脚本不能原地覆盖源目录** —— 第一版直接把译文写回 `data_chs/Text/`，
   导致校验器拿自己的输出当基线，自我比对全绿。已改为从
   `data_original/Text/`（git 恢复）读基线。
2. **git 存的是 LF**：从 `git show` 恢复的英文基线是 LF，需转回 CRLF 才能正确比对。
3. **`.gitattributes` 的 `* text=auto` 会把 CRLF 归一化成 LF** → 游戏资源必须
   `-text` 锁定，否则 checkout 后游戏读到裸 LF。已加：
   ```
   data_chs/Text/*.txt     -text
   data_original/Text/*.txt -text
   tools/*.py              text eol=lf
   ```
4. **GB2312 装不下两个排版字符**（`build_chs.py` 的 `GB2312_FALLBACK` 处理）：
   - `—`(U+2014 破折号) → `-`
   - `·`(U+00B7 姓名间隔号) → `・`
   否则 `body.encode('gb2312')` 直接抛 UnicodeEncodeError。
5. **`addon_level_06.txt` 基线是俄语**（cp1251，别人做的翻译，内容对应英文
   `addon_level_05`「to be or not to be」）。以英文 05 为底稿、参考俄语润色。
   校验器用 `BASELINE = {"addon_level_06.txt": "addon_level_05.txt"}` 改参照。
