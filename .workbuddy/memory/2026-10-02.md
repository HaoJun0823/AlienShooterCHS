- `sub_44C120` @ `0x44C120` — 16 列网格切图集

### 001font.tga 图集规格（实测）

- 覆盖：0x21-0x60 ASCII 标点/数字/大写（64）；**0x61-0xA0 全空白**；

### PE 安全特性（决定 hook 策略）
```
DllCharacteristics 0x8140
  DYNAMIC_BASE (ASLR) : True   ← 地址不固定，必须运行时算基址
  NX_COMPAT           : True
  NO_SEH              : False  ← 走 SEH

```
→ **无 SafeSEH 约束、无 CFG**，hook 方案自由度大；但 **ASLR 开启，所有地址必须
  `GetModuleHandle(NULL) + RVA` 运行时计算，不能硬编码 0x426680。**

### 两个目标函数的形态差异（关键）
- `sub_426680` @ `0x426680`（绘制循环，整体替换目标）
  入口：`push ebp / mov ebp,esp / push -1 / push SEH_426680 / mov eax,fs:[0] /
  push eax / sub esp,20h / ... / mov eax,___security_cookie / xor eax,ebp`
  → 带 **SEH frame + /GS stack cookie**，MSVC `/GS` + `/EHa`。不可裸 trampoline。
  → 引用来源：`.data` BSS 区 `0x4DA7D0`（磁盘全 0，**运行时填充的回调表**），
    说明它是被注册为对象方法/回调槽调用，不是直接 `call`。
- `sub_417F80` @ `0x417F80`（字形查找，仅观测用）
  入口：`push ebp / mov eax,[ebp+8] / test eax,eax / js / cmp eax,[ecx+2B8h] /
  jge / mov eax,[ecx+eax*4+2BCh] / test / jnz / mov eax,dword_64C4F0 / pop ebp / retn 4`
  → **11 字节 stdcall 叶子函数**，上界字段在 `this+0x2B8`，字形数组在 `this+0x2BC`。
  → 极小，inline hook / trampoline 都轻松。

### 运行时依赖
- 静态导入：`WINMM / d3d9 / d3dx9_43 / DSOUND / KERNEL32 / USER32 / GDI32 /
  COMDLG32 / ADVAPI32 / SHELL32 / ole32 / steam_api.dll`
- **`steam_api.dll` 是静态导入**（非 delay-load）→ DLL 注入必须晚于 steam_api 初始化，

  真正初始化放到首次调用 hook 函数时（懒初始化）。
- 注册表路径 `HKCU\SOFTWARE\SigmaTeam\AlienRus`，存档在 `saves/`。

### minhook 结论
**主 hook（替换 sub_426680）不需要 minhook**：因为是「整函数替换」而非「改函数中段」，
入口 `mov eax, imm32` 或 `jmp rel32` 即可，无需 trampoline 转发回原函数。
手写 5 字节 `E9` + 存原函数指针即可，比引入 minhook 更轻。

**但仍建议集成 minhook**，理由：
1. 后续若要 hook 别的函数（如 `sub_417F80` 观测码位分布、`sub_4306A0`），
   多点 hook 用 minhook 省事且不易出错
2. minhook 自带 `MH_Initialize` / `MH_CreateHook` / 指令边界自动处理，
   对 `sub_417F80` 这种小函数比自己算指令长度稳
3. 后续若改走「hook 函数中段 + 回跳原逻辑」路线，minhook 的 trampoline 是必需的
→ 建议**集成但不依赖**：核心替换自己写 E9 跳板，其余观察点用 minhook。

## winmm.dll 真相：是 Ultimate ASI Loader（22:47）

用户看到游戏目录有个 5.4MB 的 `winmm.dll`，问「为什么没被导入」。

**它确实在导入表里** —— `WINMM.dll` 是 12 个导入 DLL 的**第 1 个**（6 个函数，
IAT `0x4D92F8`–`0x4D9310`）。用户困惑的是「文件在目录里但导入表没体现」。

实际是 **DLL 搜索顺序 sideload 劫持**：
```
I:\LocalGames\AlienShooter v1.22DIC\winmm.dll
  真实身份 = Ultimate ASI Loader 9.7.4（ThirteenAG，MIT）
  原始名   = Ultimate-ASI-Loader-Win32.dll
  5.17 MB，ImageBase 0x10000000，导出 1334 个符号，GitHash 6b44066
```
Windows 对非 KnownDLLs **应用目录优先于 System32** → loader 抢先加载 →
①转发全部 winmm 导出（游戏无感）②扫描 `update\*.asi` 逐个 LoadLibrary
（= 本项目 DLL 的注入通道）。

已验证 exe 需要的 6 个 winmm 符号全由该 loader 提供（auxSetVolume 0x570E0 /
waveOutSetVolume 0x57D80 / mciSendStringA 0x572B0 / timeEndPeriod 0x57AE0 /
timeBeginPeriod 0x57AD0 / timeGetTime 0x57B10）。

**★ 结论：`WINMM.dll` 必须保持在导入表里，它是整个注入链的起点。**
抹掉它 → loader 不加载 → ASI 不注入。

## Hook 5 个 bug 修复（★★★ 22:55）—— 日志暴露了 hook 静默不装

用户反馈「应该生成 log 才对」。实际 log **生成了**（22:46），
但内容是 `[install] !! unexpected prologue - ABORT` —— hook 从未装上。

### Bug 1（致命）：prologue 校验字节写错
实测 RVA `0x26680` 前 5 字节：
```
55        push ebp
8B EC     mov ebp, esp
6A FF     push -1            ← imm8，两字节（不是 imm32 的 5 字节）
68 68 47 4D 00   push 4D4768h   ← SEH handler
64 A1 00 00 00 00   mov eax, fs:[0]
```
代码校验的是 `55 8B EC 68`（按 imm32 推的）→ 永不匹配 → 静默 abort。
**教训：MSVC 把 `push -1` 编成 `6A FF`，不是 `68 FF FF FF FF`。**
静态反汇编推导必须实测字节验证，不能凭语义猜编码长度。

### Bug 2（致命）：trampoline 回跳偏移 +8 应为 +5
原代码复现 3 条指令后 `jmp target+8`。实际那 3 条只占 5 字节，
+8 会切在 `push 4D4768h` 中间 → SEH handler 装不上 → 崩溃。
改为 `add eax, 0x26680 + 5`。

### Bug 3（致命）：naked asm 里 `mov eax, g_exe` 语义错误
`g_exe` 是变量，naked asm 里 `mov eax, g_exe` 取的是**变量地址**而非值
→ 跳到无关地址 → 崩。
解法：新增 `extern "C" BYTE* __cdecl CHS_GetExeBase() { return (BYTE*)g_exe; }`
（编译为 `mov eax,[g_exe]; ret`），asm 里改为 `call CHS_GetExeBase`。

### Bug 4：日志格式化不支持宽度/零填充
`my_snprintf` 不解析 `%02X` 的 flag/width，整行退化成字面量
`"%02X %02X %02X %02X"` —— **完全看不出实际字节值，极度误导排障**。
已重写：抽出 `my_vsnprintf(char*,size_t,const char*,va_list)` 内核，
`my_snprintf` 与 `LogPrintf` 共用，支持 flags/width/precision（`%02X`/`%06X`/`%.2f`）。
`LogPrintf` 原本二次解析也丢 width，改为直接转发 my_vsnprintf。

### Bug 5：`RVA_NullGlyph` 当绝对地址用
`font == (void*)RVA_NullGlyph` —— RVA 是相对值，ASLR 下 exe 基址实测
`0x3E0000`（≠ ImageBase 0x400000），运行时地址应是 `0x3E0000 + 0x24C4F0`。
该比较永不成立，null-glyph 分支统计失效。
改为 `g_exe + RVA_NullGlyph`。

### 附加改进
- prologue 校验改为逐字节比对 + 失败时 dump 实际 16 字节（原来只一句 ABORT）
- 新增**写后读回校验**：E9 写完立即读回比对 5 字节
- 新增 **AutoDumpIfDue()**：每 2000 次调用自动落盘 `[auto-dump]`
  （此前 `CHS_Dump` 导出无人调用，游戏里没有外部调用者）
- `block_layout.h` / `README_HOOK测试.md` 的 prologue 注释全部更正

## 排查「日志没生成」（23:10）

用户启动游戏后找不到 `chs_probe.log`。

### 事实
- 旧日志（22:46 那份）**确实在 `I:\LocalGames\AlienShooter v1.22DIC\chs_probe.log`**，
  证明路径逻辑与加载链都工作过；22:56 部署新版时被我删除
- 游戏进程已退出；全盘搜索确认新日志确实不存在 → **新版 DLL 根本没被加载**，
  连 DllMain 都没跑（若跑了，至少会因旧代码路径写出一份头部）

### 排查 loader 行为（关键发现）
Ultimate ASI Loader 是 C++ / `std::filesystem` 写的，**字符串以 UTF-16 存储**。
最初扫 ASCII 什么都找不到，扫 UTF-16 才拿到真相：

```
*.asi                       ← 它扫这个模式
update                      ← 默认 update 目录
update\global.ini           ← 可选配置（不存在也能跑，用默认）
plugins\scripts\global.ini
%s\%s\%s.%s.log              ← loader 自己也有日志格式
Select Override (Update) Folder
Ultimate-ASI-Loader-Win32.dll
modloader\modloader.asi
```
→ **确认 loader 会扫 `update\*.asi`**，`global.ini` 缺失不是原因。
（另：`.rsrc` 段 1.4MB，entropy 5.87，里面可能也藏了目录名。）

### 真正的改进：日志写入加保险
原代码只在 `InstallHook()` 内部才 `LogOpen()`，且只写 exe 目录一处。
若 DllMain 在此之前失败 / 目录不可写，就毫无痕迹 —— 无法区分
"没被加载"与"加载了但失败"。

改动：
1. 新增导出入口 `CHS_LogBoot(HMODULE)`，在 `dllmain.cpp` 的
   `DLL_PROCESS_ATTACH` 里**第一件事**就调用（早于 `CHS_Init`）
   → "DLL 被加载"与"hook 装上"现在有**独立证据**
2. 日志**三处落盘**：`<exe目录>\chs_probe.log`（主，覆盖写）
   + `<dll目录>\chs_probe_DLLDIR.log` + `%TEMP%\chs_probe_TEMP.log`（追加）
3. 头部加 `pid` / `dll path` / `log path`，便于确认是哪个副本在跑

### 构建事故
改 `g_log` / `LogWrite` 时因新旧两份并存导致
`C2374 重定义` / `C2084 已有主体` / `C2065 未声明`。
解法：删掉文件顶部旧定义，只保留「日志」小节里那一份。

### 现状
`dist\AlienShooterCHS.dll` 10240 字节，MD5 `a82038ab322ff9f35856e7e048b40ce4`，
已部署 `update\AlienShooterCHS.asi`。
