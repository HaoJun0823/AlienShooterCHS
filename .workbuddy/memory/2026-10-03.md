## 崩溃根因：thiscall 的 ecx 未恢复（★★ 本次核心）

现象：日志显示 `[install] write-back verified OK` / `hook armed`，
然后游戏立刻崩，**一条 ProbeBlock 记录都没有**。

根因（IDA 证据）：
```
4266A8  mov esi, ecx      ← ecx 就是 this（__thiscall）
4266AA  mov ebx, [esi+1Ch]
```
`CHS_Hook`（naked）里写的是 `push ecx; call ProbeBlock; add esp,4` 然后跳回
原函数。`ProbeBlock` 是 `__cdecl`，**ecx 属于 caller-saved**，返回后 ecx 已是
垃圾 → `mov esi, ecx` 拿野指针 → `[esi+1Ch]` 访问违例。

修复：压两份 ecx，一份当参数、一份留着恢复：
```
51            push ecx      ; 保存 this
51            push ecx      ; 参数
E8 A9000000   call ProbeBlock
83 C4 04      add esp, 4
59            pop ecx       ; 恢复 this
55 8B EC 6A FF              ; trampoline
E8 .. 05 85660200 FF E0     ; jmp target+5
```
已用 pefile 扫 dist DLL 逐字节校验：`51 51 E8 A9 00 00 00 83 C4 04 59 ...` ✓

### ★ freestanding 下启用 MSVC SEH 的方法（可复用）
`__try/__except` 需要两个 CRT 符号，我们 /NODEFAULTLIB：
- `__load_config_used`：自己定义，`.rdata$lcfg` 段 16 个 DWORD，首值 0x40
  （SEHandlerTable/Count=0 ≡ /SAFESEH:NO）。C 里写 `_load_config_used`，
  x86 装饰后正好是 `__load_config_used`
- `__except_handler3`：**VC 的 msvcrt.lib/libcmt.lib/libvcruntime.lib 里都没有**。
  但 **msvcrt.dll 导出 `_except_handler3`**，且 MSVC x86 生成的正是 handler3
  作用域表 → 写一个裸跳转桩等价导入 thunk：
  ```c
  static void* g_pExceptHandler3 = NULL;   // DllMain 里 GetProcAddress 填
  ```

## 05:36-05:48 第九轮：崩溃 —— `pos` 推进冲出队列缓冲区

### 崩溃现场
```
[man] D3DXCreateTexture ok tex=19AB8B40  (GetLevelDesc hr=0x00000000 -> 0x0, informational)
=== CRASH ===
code=0xC0000005  EIP=6F873AD5  (INSIDE AlienShooterCHS, +0x3AD5)
fault = 0 READ   EAX=00000004 EDX=19AB8B40
```
用新加的 `/MAP` 定位：`ManDrawLine` RVA=**0x3AC0**，
`0x3AD5 = 入口+0x15`。反汇编该处是
`8D 46 04 / 66 83 78 FC 00`（= `lea eax,[esi+4]; cmp word ptr[eax-4],0`），
正是**扫宽字符串找 NUL 的循环** ⇒ `s` 是野指针。

### 根因：行推进没有硬上限
```c
// 旧代码（CjkFlush 与 D3DX 兜底路径各一份）
int k = 0;
while (pos + k < CJKQ_CHARS && it->t[pos + k]) ++k;
pos += k + 1;
```
`it->t` 是 `WCHAR[256]`。**若整段没有 NUL 终止符**，
`pos + k == CJKQ_CHARS - 1` 时循环停下，`pos += k+1` ⇒ `pos == 256`
已经越过数组末尾；下一轮 `it->t + pos` 就是野指针。
`nl`（行数）与实际 NUL 数量不一致时必然触发。

### 修复（三层）
1. `ManDrawLine` 入口 `IsBadReadPtr(s, 2)` + 每 16 字复查一次可读性
2. 扫到 `MAN_MAXSTR` 仍无 NUL ⇒ 丢弃该行（否则 `ExtTextOutW` 也会读越界）
3. `CjkFlush` 两处推进改成硬上限：
   ```c
   while (pos + k < CJKQ_CHARS - 1 && it->t[pos + k]) ++k;
   if (pos + k >= CJKQ_CHARS - 1) { pos = CJKQ_CHARS; break; }  // 无终止符，停
   pos += k + 1;
   ```
4. 像素上传循环加 `IsBadReadPtr(src/dst)` 守卫（下一个潜在崩溃点）

### ★ GetLevelDesc -> 0x0 也说明我猜的 D3DDESC9 偏移不对

`build.bat` 的 link 加 `/MAP:"%OUT%\AlienShooterCHS.map"`，崩溃时
`EIP - 模块基址 = RVA`，在 .map 里 `grep 函数名` 得 RVA，

### 崩溃现场
```
=== CRASH ===  EIP=6F873FD7 (INSIDE AlienShooterCHS, +0x3FD7)
fault = E4 READ   EAX=00000000  ESI=00000000  EBX=0000000C
```
MAP 定位：`ManDrawLine` RVA=0x3AC0，`0x3FD7 = +0x517`。
字节 `8B 07` = `mov eax,[edi]`；`8B B0 E4 00 00 00` = `mov esi,[eax+0xE4]`。
**0xE4 = 57*4 = `dvt[VTI_SETRENDERSTATE]`** ⇒ 崩在取设备函数指针那几行。

### 根因：「设备指针非空」≠「设备指针有效」
```c
void** dvt = *(void***)dev;      // dev 非空，但已失效 → dvt == NULL
srs = (SetRenderState_t)dvt[57]; // 读 0+0xE4 → AV
```
旧代码只查 `if (!dev) return -1`，没查虚表。设备在 Reset/设备丢失后
就是野指针 —— 这正是当初装 `Reset` 钩子的原因。

### 修复（把"有效"贯彻到底）
1. `ManDrawLine` 入口 `LooksLikeDevice(dev)`（验证虚表前 4 项落在 d3d9.dll 内）
2. 取虚表后 `IsBadReadPtr(dvt, 0x1B0)`（0x1B0 = 108*4 > 最大槽 107*4）
3. 每个函数指针再过一遍 `InD3d9()` —— 索引错一位会读到"恰好非空"的
   相邻槽，call 过去就是随机崩
4. `CjkUpdateMapping` 的守卫从 `0xD0` 放宽到 `0x1B0`（0xD0 不覆盖 107 槽）
5. `LooksLikeDevice` 的 `IsBadReadPtr(vt, 0xD0)` 收紧到 `0x30`（只需读前 4 项）
6. **`ManEnsure` 里把纹理与设备绑定**：
   - 设备无效 / 设备换了 / 纹理对象虚表不可读 ⇒ 一律丢弃 `g_tex` 重建
   - `g_texProbeDev` 记录探测所属设备，换设备则作废探测结果重探
     （不同驱动的虚表布局未必相同）

## 05:53-06:15 第十二轮：崩溃在栈地址 —— `__stdcall` 参数个数不符把栈啃掉

### 崩溃现场
```
=== CRASH ===  EIP=20F69C  (outside known modules)
fault = 20F69C WRITE   ← 写入的是**栈地址**（ESP=20F664，EIP=ESP+0x38）
EAX=0020F6C0 ECX=0020F69C EDX=0 ESI=0020F69C EDI=08A56BE0 EBX=768FCA30
calls = 1
```
`ECX == ESI == EIP == 栈地址` + `WRITE` 违例 = **跳到栈上执行**。
`[man]` 一行都没有 ⇒ 崩在 `ManEnsure` 里新增的 `CjkGetStateBlock`。

### ★★★ 根因：`__stdcall` 的 `ret N` 与我们的参数个数不符
上一版 `CjkGetStateBlock` 是"盲扫 `dev vtbl[100..110]`，逐个当 CreateStateBlock 调"：
```c
hr = f(dev, 1, &sb);   // f 可能是 SetStreamSource / DrawPrimitiveUP / Present…
```
D3D9 全部方法都是 `__stdcall`，callee 用 `ret N` **自己清栈**。
我们把 3 个参数压进去，若 f 实际是 `Present`（5 参，`ret 20`），
callee 会多弹 8 字节；若 f 是 `GetAvailableTextureMem`（0 参，`ret 4`），
callee 少弹 8 字节。**无论哪种，ESP 都会偏**，返回地址随即被踩，
函数返回时跳到栈上执行。

### ★★ 关键认知：`__try/__except` 抓不住这类错误
它不是异常，是**栈被一点点啃掉**。SEH 只能拦 AV，拦不住 ESP 失衡。
→ 这正是为什么这一轮"零日志、直接崩在栈上"。

### 修复
**① 不再盲扫，用推导出的槽位。** 从已实测锚点顺推：
```
57 SetRenderState  ← 实测（75 处调用）
58 GetRenderState  59 CreateStateBlock ← 要的
60 BeginStateBlock 61 EndStateBlock
62 SetClipStatus    63 GetClipStatus
64 GetTexture       65 SetTexture             ← 65 实测
66 GetTextureStageState 67 SetTextureStageState ← 67 实测
68 GetSamplerState      69 SetSamplerState      ← 69 实测
... 83 DrawPrimitiveUP ← 实测 ... 89 SetFVF ← 实测
```
整条链与**三个独立实测点**完全吻合 ⇒ `CreateStateBlock=59` 可信。

**② 新增不用 callee 清栈的安全调用桩**（naked asm）：
```c
extern "C" __declspec(naked) long __cdecl CjkSafeCall3(void* fn, void* a1, void* a2, void* a3)
{
    __asm {
        push ebx / push esi / push edi / push ebp
        mov eax,[esp+20]  mov ebx,[esp+24]  mov ecx,[esp+28]  mov edx,[esp+32]
        push edx / push ecx / push ebx
        mov ebp, esp              // 记住压完参数的 ESP
        test eax,eax / jz skip
        call eax
    skip:
        mov esp, ebp              // ★ 无条件恢复 ESP，无视 callee 的 ret N
        add esp, 12               // 丢弃参数
        pop ebp / pop edi / pop esi / pop ebx / ret
    }
}
```
另配 `CjkSafeCall5`（纹理探测：tex,Level,pLockedRect,pRect,Flags）。
**从此所有"槽位不确定"的调用一律走它**，参数个数猜错也只是调用失败，不崩。

**③ 探测缓冲加垫**：`CjkProbeTex` 原用 8 字节 `ManLockedRect lr` 接结果。
若那个槽其实是 `GetLevelDesc`，它会写 ~124 字节的 `D3DDESC9` → **砸栈**。
改用 256 字节 `pad[256]`，再按偏移取 `Pitch`(0) / `pBits`(4)。

**④ 失败即安全退出**：`CreateStateBlock` 拿不到 ⇒ `g_sbState=-1`
（只报一次）⇒ `ManEnsure` 返回 0 ⇒ **完全不画**，UI 保持原样。

## 06:15-06:35 第十七轮：★★★ 抓到「文本空白」的真凶 —— D3DPOOL_MANAGED 写成 3（= SCRATCH）

### 现象

`traceA/B` 各 206 次而 `traceC/trace5` 各 1 次 ⇒ **第 2 次起在 traceB 与 traceC

### 真凶一（空白）：`g_gettersFail` 逻辑写反
```c
if (g_gettersFail == -1) return -1;
g_gettersFail = -1;   // ← 成功路径也置成“失败” ⇒ 第 2 次起永久停画
```
第 1 次成功后把它置 −1，之后每次都命中 `== -1` 直接 return。
⇒ **只有第一块文字被画出来，其余全空白**。
修法：`== -1` 只在**真的取不到 GetRenderState/GetFVF** 时才置。

### 真凶二（空白，更根本）：D3DPOOL / D3DTA 枚举值写错
```c

#define D3DTA_TEXTURE_   1   // ★ 1 是 D3DTA_CURRENT！TEXTURE 真值 = 2
```
`D3DPOOL_SCRATCH` 的纹理**永远不能被设备使用**（只能当暂存介质）：
- `LockRect/UnlockRect` 一切正常（`pitch=2560=640*4`，完全正确，所以探测过了）
- `SetTexture` 绑上去也返回成功

这就是为什么「所有自检都绿、画面却空白」。
`D3DTA_TEXTURE_=1` 其实是 `D3DTA_CURRENT`（第 0 级恰好等价于 TEXTURE，纯属侥幸）。

### 真凶三（特别卡）：字体每帧重建 + trace 永远不关
1. **字体**：实测同一帧有两种字号（10 / 18）**交替出现**，而旧代码
   `if (g_hfont && g_fontPx != px) { DeleteObject; CreateFontW; }`
   ⇒ 等于「每画一行重建一次字体」。`CreateFontW` 是 GDI 最慢的调用之一，
   帧率直接被打到个位数。而且 `DeleteObject` 一个**仍被 SelectObject**
   的字体是失败的 → GDI 句柄泄漏。
   → 改为 `ManFontFor/ManSelectFont` 按字号缓存 6 个 HFONT，切换只做一次
     `SelectObject`；淘汰时先 `SelectObject(GetStockObject(SYSTEM_FONT))` 再删。
2. **trace 永远不关**：`int trace = (g_manDraws < 2)` —— 成功计数不增就永远为真，
   于是每次绘制都 `LogPrintf + FlushFileBuffers`（206 次刷盘）。
   → 改成倒计数 `g_traceLeft`（最多 4 次），结构上不可能失控。

### 真凶四（卡）：CjkUpdateMapping 每块文本都跑一遍

→ 加缓存：同一设备上最多每秒复查一次（分辨率/设备变化仍能跟上）。

### 其它

（`clear=1` / `begin=0` / `present=0` 说明既不是清屏，也拿不到任何帧回调。）

### 解法（已实机验证 ✅）
**每识别出一项，就把"本帧到目前为止的全部四边形"重画一遍**（一次调用）。
前面那些批次被丢弃无所谓 —— **最后一次必然包含本帧全部内容**。

帧边界：本作**不调 BeginScene/EndScene/Present**（dev 与 swapchain 全 0），
拿不到回调 ⇒ 用**文本签名**判定：
> 同一个 `(文本, 位置, 字号)` 在本批里重复出现 = 新的一帧开始了 ⇒ 整批作废

```c
// ManDrawLine 里，rasterize 之前
unsigned long sig = ManSig(s, n, ax, ay, px);
if (ManSigSeen(sig)) ManQuadReset();     // 新帧
ManSigAdd(sig);
...
// rasterize + ManEmitQuad(...) 之后
ManDrawQuads(dev);                       // 把本帧全部四边形重画一遍（一次 UP 调用）
```
`ManDrawQuads` 内含完整的「状态保存一次 / 设置一次 / 还原一次」，
全部四边形走同一条 `DrawPrimitiveUP`（`STRIDE=28`，`TRIANGLIST`，`nQuads*2` 个图元）。

## 07:30-07:50 第二十二轮：★ 帧末钩子（根因级修复）+ 字体可配置 + 字号补偿 → 发行版

### ★★★ 空白/闪烁的统一根因（三条实机对照实验）
| 实验 | 结果 |
|------|------|
| 一次 DrawPrimitiveUP 画 2 个四边形 | 两个都出现 |
| 两次调用、紧挨着、中间无状态改动 | 两个都出现 |
| 两次调用、**中间夹着引擎的绘制** | **只剩最后一个** |
⇒ 本作这个 D3D9 实现下，被别的绘制隔开的 UP 调用只有最后一笔落屏。
菜单文本恰好最后画 ⇒ 可见；游戏内 HUD 画在世界之前 ⇒ 被盖住（看不见 / 闪）。

### ★★ 解法：帧末钩子（改 exe 代码，不走虚表）
IDA 逐条核对出引擎帧末：
```
3041E  mov eax,[edi+0E28h]      ; 8B 87 28 0E 00 00 —— 正好 6 字节
30424  lea edx,[ebp-14h] ...    ; 复原后跳回这里
30433  call dword ptr [ecx+44h] ; Present —— 全 exe 唯一
```
- 虚表钩 Present(17) **实测计数恒 0**（orig 却是 d3d9 真函数）⇒ 不可靠；
  直接在 0x3041E 写 `E9 rel32 + 90`，裸汇编 pushad/pushfd → ManFrameEndFlush
  → popfd/popad → 复原 `mov eax,[edi+0E28h]` → `jmp [g_frameResume]`
- 装不上时自动退回旧行为（不会变成完全不显示）
- 引擎设备 = `[screen+0xE28]`（`CjkActiveDevice()`），实测与本进程捕获的同一个 `same=1`
- 一帧一次 ⇒ 状态保存/设置/还原从"每项一次"降到"每帧一次"（大幅提速）

### ★★ 猜帧的教训（第 22 轮中途踩到）
曾把帧边界改成"时间间隔 > 8ms 即新帧"，实测一帧内文本项间隔就有 **15~63ms**
（GDI 栅格化+上传本身就贵）⇒ 同帧被切成多段 ⇒ 每段前面的项被丢 ⇒ 难度/结算屏**整帧空白**。
**帧边界只能靠引擎自己的帧末回调。**

### 字体（用户需求）：update\chs.ini 可配置 + 自动族名
- `[font] file=默认 SourceHanSansHWSC-VF.ttf / face=（留空自动读 name 表）/
  quality=4 / scale=0`
- `AddFontResourceExW(FR_PRIVATE)` 私有加载；族名候选 = ini face → ttf 英文名(0x409)
  → 中文名(0x804) → 文件名去扩展名，**每个都用 GetTextFaceW 回读校验**（GDI 会静默换字体），
  全失败回退 SimSun；日志打印实际族名与回退原因
- ★ 日志里 `%ls` 打宽字符在 GBK 日志下会花，改用 `CjkWToA`（非 ASCII → '?'），
  于是日志显示 `using face = "???? HW VF"` = "思源黑体 HW VF"

### ★★ 字号偏小 / 位置偏下（用户两个问题，已量化）
`lfHeight` 是**单元格高度**，"单元格 = 几个 em"由字体定：
| | upem | winAsc/Desc | cell | em@lfH18 | 中 墨高@lfH18 | 墨顶离格顶 |
|---|---|---|---|---|---|---|
| SimSun | 256 | 220/36 | 1.000 em | 18.00 | 16.52 | 0.70 px |
| 思源黑体 | 1000 | 1160/288 | 1.448 em | 12.43 | 11.42 | 3.98 px |
- **小 31%** 的原因 = cell/upem 比例不同（0.69）
- 补偿：`pxUse = px * (winAsc+winDesc)/upem`（`TtfReadVert()` 从 ttf 读，scale 可覆盖）
  → 墨高 16.51 ≈ SimSun 16.52 ✔（残差 0.01px）
- **靠下** = 单元格顶 ≠ 墨迹顶；补偿后偏移 5.74px（SimSun 只有 0.70px）
  ⇒ 思源黑体 winAscent(1160) > upem(1000)，格顶到 em 顶还空 160/1448 ≈ 11%
- SimSun 另有内嵌点阵 ppem=12..17（EBDT/EBLC），10~16px 走位图更实更黑 ⇒ 显得更大
- 未做：按墨迹 bbox 对齐锚点（我们本来就在扫 DIB 像素），或 ini 加 `yoff=`
