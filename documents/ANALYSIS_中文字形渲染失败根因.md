# Alien Shooter v1.22DIC 中文字符渲染失败 — 逆向分析报告

分析对象：`I:\LocalGames\AlienShooter v1.22DIC\AlienShooter.exe`
- MD5 `641f33c3207d37a838d4f7f8f9c40e26` / SHA256 `4dd960458d6fffcc9d00e9e7ba492739fb6d530d4c0b302f1c6baa8b55d9b142`
- 32 位 PE，ImageBase `0x400000`，MSVC 编译，DirectX 8/9（`d3d9` + `d3dx9_43`）
- 5456 函数 / 1511 字符串
- 分析工具：IDA Pro + ida-pro-mcp（headless idalib，session `cf92cf00`）

---

## 一、结论先行

中文无法渲染**不是编码问题，也不是缺字体文件**，而是两个硬性设计限制叠加：

1. **引擎按「单字节」处理文本**，逐字节查表，完全没有 UTF-8 / GBK 双字节序列的解码逻辑。
2. **位图字体图集里根本没有汉字**，`Font\001font.tga` 只有 152 个字形，全是 ASCII 与俄文 CP1251。

任意中文字符的字节序列都会被拆成 2~3 个独立字节，每个字节去查一张「俄文字母表」，结果必然是乱码或空白。

换言之：**这个引擎在设计时就不具备渲染 CJK 的能力**，不是配置能改好的。

---

## 二、渲染链路（已逐函数确认）

### 1. 文本绘制主循环 — `sub_426680` @ `0x426680`

游戏所有文字都经过这个函数（菜单、HUD、提示）。核心循环：

```c
v20 = *(_BYTE *)(*v14 + v10);        // 0x42694A  取「一个字节」
...
if ( v20 >= 0x20u )                  // 0x4269A5  过滤控制字符
{
    *((_DWORD *)Block + 3) = v20;                        // 当前字符码
    (*(void (__thiscall **)(int, char *))(*(_DWORD *)v2 + 12))(v2, Block);  // 虚表[3] 绘制
    ...
}
*((float *)Block + 12) = *(float *)(v2 + 28) + *((float *)Block + 12);  // 按字宽推进 X
```

关键点：读取用的是 `*(_BYTE *)`，即**逐字节**。代码里没有任何 `IsDBCSLeadByte` / `MultiByteToWideChar` 之类的判定分支。
（`MultiByteToWideChar` 虽然被导入，但那是 CRT 运行库自带的，与文本渲染无关。）

支持的转义序列仅有两个：`\n`(10) 换行、`\r`(13) 回车；`\t`(9) 按字宽 7 倍跳空格；`\x1B`(27) 后跟可打印字符为颜色转义。

### 2. 字形查找 — `sub_417F80` @ `0x417F80`

```c
int __thiscall sub_417F80(_DWORD *this, int a2)
{
  if ( a2 < 0 )                    return dword_64C4F0;
  if ( a2 >= *(this + 174) )       return dword_64C4F0;   // 上界检查
  result = *(this + 2 + a2 + 175);                        // glyph[a2]
  if ( !result )                   return dword_64C4F0;   // 空槽回退
  return result;
}
```

索引 `a2` 是**单字节值**，有效范围被 `this[174]` 硬性限制。配套的 `sub_417F50` (`0x417F50`) 是它的布尔版本，判定条件完全一致。

### 3. 字形表容量 — 固定 256 项

`PICTURE_FONT` 的 vtable 在 `0x4DA5D8`（RTTI 名 `??_7PICTURE_FONT@@6B@`）。其中 `vtbl[3] = 0x44A6A0` 即加载函数，其中一段：

```c
*(int *)(*(this + 2) + 4) = 256;   // 0x44A816   字形表容量 = 256，写死
```

`this + 2` 指向字形槽数组，偏移 +4 是「容量」字段，**硬编码为 256**。这是单字节字符集的必然上限，无法容纳多字节编码。

### 4. 图集切格 — `sub_44C120` / `sub_44BA60`

```c
// sub_44BA60 @ 0x44BA60 —— 16 列网格切分
v10 = v2[2] % 16 * (v2[4] + 1);   // 列内偏移
v6  = v2[2] / 16 * (v2[4] + 1);  // 行基址
for (v3 = 0; v3 < rows; v3++)
  for (i = 0; i < cols; i++)
    sub_44BE60(i, v3, sub_448E20(atlas, i + v10, v3 + v6));  // 逐格搬运像素
```

`v2[2]` 是图集宽度，除以 16 = 每行格数。像素读写由 `sub_448E20` / `sub_44BE60` 完成，按 bpp 支持 8/16/24/32 位。

## 三、Font\001font.tga 图集实证

### 文件头（TGA uncompressed true-color）

| 文件 | 尺寸 | bpp | 类型 | 用途 |
|------|------|-----|------|------|
| `001font.tga` | 208 × 288 | 24 | 直存 RGB | **主字形图集** |
| `002font.tga` | 128 × 160 | 16 | 直存 RGB565 | UI 装饰图，非字形 |
| `003font.tga` | 96 × 128 | 16 | **RLE 压缩** | 小图标 |

### 网格参数（实测反推）

- 格宽 = 208 / 16 = **13 px**
- 格高 = **18 px**（由逐行墨迹分布确定：墨迹占 y=0..12，y=13..17 恒空）
- 网格 = 16 列 × 16 行 = 256 格
- **映射公式：`code = cell_index + 0x21`**

映射验证（渲染出的字形与 ASCII 对照）：

| cell | code | 渲染结果 |
|------|------|----------|
| 0x00 | 0x21 `!` | 竖笔 + 点 ✓ |
| 0x0F | 0x30 `0` | 圆角矩形 ✓ |
| 0x1F | 0x40 `@` | 外框 + 内框 ✓ |
| 0x20 | 0x41 `A` | 三角 + 横杠 ✓ |
| 0x2F | 0x50 `P` | 上竖 + 上横 + 中竖 ✓ |
| 0x40 | 0x61 `a` | **全空白** |

注意：`0x20`（空格）本身没有字形（cell 索引 -1），`0x21` 起才是 `!`。

### 字形覆盖统计（关键）

```
字形总数: 152
码位范围: 0x21 - 0xFF

  0x21-0x60  (64)  ASCII 标点、数字、大写字母
  0x61-0xA0  (--)  全空白 —— 小写字母完全没有字形
  0xA1-0xAF  (15)  俄文 CP1251
  0xB1-0xCF  (31)  俄文 CP1251
  0xD2-0xF0  (31)  俄文 CP1251
  0xF2-0xFF  (12)  俄文 CP1251 尾部
```

**这张图集是给俄语原版设计的**（Sigma Team，俄罗斯开发商），高位区放的是单字节俄文 CP1251 字母，不是 GBK 汉字。

顺带发现：**0x61–0xA0 整段空白意味着连小写英文字母都显示不出来** —— 这是该版本字体图集的自身缺陷（`strings.ini` 里所有文本被迫全大写，正是为了绕过这个问题）。

## 四、失效机理推演

以 UTF-8 的「你」为例（`E4 BD A0`）：

| 字节 | 落入码位 | 图集里的字形 | 屏幕结果 |
|------|----------|--------------|----------|
| 0xE4 | 0xE4 | 俄文 `т` | 画出一个错的俄文字母 |
| 0xBD | 0xBD | 俄文 | 画出一个错的俄文字母 |
| 0xA0 | 0xA0 | **空白** | 什么都不画 |

若改用 GBK 编码（`C4 E3`），同样落到俄文区，结果一样错。

三个字节各自独立前进（每个都按 `v2+28` 的字宽推进 X），所以中文不但错乱，还会**占据 3 倍宽度**，排版彻底崩坏。

## 六、可行的修复方向（评估）

### 方向 A：DLL Hook 替换字形查找 ★推荐

在 `sub_417F80` 上做 inline hook，改为：
1. 拦截 `sub_426680` 的逐字节循环 —— 但循环本身是内联的，粒度太细，逐字节 hook 成本高。

更合适的做法是**整体替换 `sub_426680`**，在 DLL 内重写一套 UTF-8 → 字形索引的转换，配合自建的 CJK 字形图集（替换 `001font.tga` 或旁挂一份）。工作量集中在：
- 字形图集生成（用 Clairvaux.xfc 之类的中文字体渲染成同规格 TGA）
- 绘制循环重写（需复刻对齐、换行、颜色转义、Tab 行为）
- 字宽表、`<Font=N>` 标签、ESC 颜色码兼容

风险：需复现 `Block` 结构体偏移语义（`Block+12`=X, `Block+13`=Y, `Block+116`=文本指针, `Block+31`=长度, `Block+32`=对齐标志, `Block+34`=行数等）。

### 方向 B：单字节重编码（Transcode-only）★低成本备选

不改引擎，改用**自定义单字节编码**：把常用汉字（3500 一级 + 常用二级，约 7000 字）映射到 0x80–0xFF 之上的扩展区，**但这会超出 256 项容量上限**，所以必须配合方向 A 的表扩容。

若只做 256 字以内的小字集，可以塞进现有 0x61–0xA0 空白区，但 256 字远不够汉化一部游戏。

### 方向 C：换 GDI 渲染

游戏已导入 `CreateFontA` / `ExtTextOutA` / `GetTextExtentPoint32A`（GDI32），说明某些 UI 元素走 GDI。但游戏主体是 D3D9 全屏 blit，GDI 路径无法覆盖游戏内文字。仅适合处理菜单类界面。

### 不推荐

- 直接改 `001font.tga` 塞汉字 —— 容量 256 是硬限制，改图集无法突破「单字节 → 256 槽」这个模型。
- 修改 `code = cell + 0x21` 的偏移 —— 只解决映射起点，不解决编码识别问题。
